# pgbench_socket_test

Бенчмарк Unix domain sockets на реальной нагрузке: трафик между `pgbench` и PostgreSQL
записывается, а потом проигрывается заново через UDS или TCP. Так измеряется сам
транспорт, без времени выполнения SQL.

Работа идёт в два этапа:

1. **Запись** (`record.sh`). `pgbench` подключается не к PostgreSQL напрямую, а к прокси
   на `socat`. Прокси пересылает трафик серверу и сохраняет все байты каждого соединения
   в файлы.
2. **Воспроизведение** (`replay`). Фейковый сервер отвечает записанными ответами, а клиент
   отправляет записанные запросы и измеряет пропускную способность и задержки.

```
запись:   pgbench ──► proxy/.s.PGSQL.5432 ──► socat (пишет trace/) ──► pgsock/.s.PGSQL.5432 ──► PostgreSQL
replay:   replay client ──► unix:... или tcp:... ──► replay server (отдаёт ответы из trace/)
```

## Требования

- PostgreSQL с `pgbench`
- `socat`
- компилятор C и `make`

## Обозначения

Команды ниже используют две переменные окружения. Задайте их под свою установку:

```bash
export PGBIN=/path/to/postgresql/bin    # каталог с pg_ctl, createdb, pgbench, psql
export PGDATA=/path/to/data             # каталог данных кластера (initdb -D ...)
```

Если бинарники PostgreSQL уже есть в `PATH`, `PGBIN` можно не задавать. Тогда уберите
префикс `$PGBIN/` из команд. `record.sh` тоже читает `PGBIN`, а без неё берёт `pgbench`
из `PATH`.

Все команды запускаются из корня репозитория.

## Подготовка (один раз)

### 1. Запустить PostgreSQL с сокетом в папке проекта

`record.sh` ожидает сокет сервера в `pgsock/.s.PGSQL.5432`:

```bash
mkdir -p pgsock
$PGBIN/pg_ctl -D $PGDATA -l pg.log -o "-k $PWD/pgsock -c listen_addresses=''" start
```

`-c listen_addresses=''` отключает TCP, сервер доступен только через сокет. Остановить
сервер:

```bash
$PGBIN/pg_ctl -D $PGDATA stop
```

Если сервер был запущен иначе (например, с сокетом в `/tmp` или `/run/postgresql`), в
`pgsock/` может остаться старый файл сокета. `record.sh` его увидит, но подключиться не
сможет. В этом случае перезапустите сервер командой выше.

### 2. Разрешить вход без пароля

В `$PGDATA/pg_hba.conf` выше остальных `local`-строк должна стоять строка:

```
local   all   all   trust
```

Это нужно для воспроизведения: при `scram-sha-256` и `md5` сервер в каждой сессии
присылает новую случайную соль, и записанный вход не пройдёт. Применить изменения:

```bash
$PGBIN/pg_ctl -D $PGDATA reload
```

`trust` пускает любого локального пользователя под любой ролью без пароля. На общей
машине верните прежнюю настройку после экспериментов.

### 3. Создать базу `bench`

```bash
$PGBIN/createdb -h $PWD/pgsock -T template0 bench
$PGBIN/pgbench  -h $PWD/pgsock -i -s 1000 -I dtGvp bench
```

- `-s` — масштаб. Каждая единица — 100 000 строк в `pgbench_accounts`, примерно 15 MB
  на диске; `-s 1000` — около 15 GB. Размер базы почти не влияет на байты в сокете, так
  что для записи большой масштаб не нужен.
- `-I dtGvp` генерирует данные на стороне сервера. Это намного быстрее, чем генерация
  по умолчанию.

### 4. Собрать replay

```bash
make
```

## Запись трафика

```bash
./record.sh                              # по умолчанию: -c 8 -j 8 -T 10 -M prepared
./record.sh -c 4 -j 4 -T 30 -M simple    # любые опции pgbench
```

Каждый запуск создаёт папку `trace/<ГГГГММДД-ЧЧММСС>/` (путь переопределяется переменной
`TRACE`). В ней лежат файлы для каждого соединения:

| Файл | Содержимое |
|---|---|
| `c2s.PID.bin` | все байты клиент → сервер, как они были отправлены |
| `s2c.PID.bin` | все байты сервер → клиент |
| `log.PID.txt` | лог `socat -v`: время и размер каждого куска, ошибки |
| `pgbench.txt` | вывод pgbench |

`PID` — номер процесса socat, обслуживавшего соединение. Помимо рабочих соединений
pgbench открывает одно короткое служебное; `replay` его пропускает (опция `-m`).

Пропускная способность pgbench во время записи не является результатом: socat добавляет
лишнее копирование и переключения контекста на каждое сообщение.

## Воспроизведение

Ниже `trace/<запуск>` — папка одного запуска `record.sh`.

### Статистика трейса

```bash
./replay info -d trace/<запуск>
```

### UDS и TCP

Сервер и клиент запускаются отдельно, в двух терминалах:

```bash
# Unix domain socket
./replay server -d trace/<запуск> -a unix:$PWD/replay.sock
./replay client -d trace/<запуск> -a unix:$PWD/replay.sock -c 8 -T 10

# TCP loopback для сравнения
./replay server -d trace/<запуск> -a tcp:127.0.0.1:15432
./replay client -d trace/<запуск> -a tcp:127.0.0.1:15432 -c 8 -T 10
```

Пример вывода клиента:

```
target:     unix:/path/to/replay.sock
traces:     2 from trace/<запуск>, clients: 2
rounds:     2071629 in 5.000 s = 414325 rounds/s
data:       client->server 22.40 MB/s, server->client 14.85 MB/s
latency us: avg 4.80  p50 4.67  p90 5.39  p99 9.39  p99.9 16.25  max 1657.54
```

### Против настоящего PostgreSQL

```bash
./replay client -d trace/<запуск> -a unix:$PWD/pgsock/.s.PGSQL.5432 -R
```

Проходит только один проход по трейсу (`-n 1`, по умолчанию). В режиме `-M prepared`
второй проход заново отправит Parse, и сервер ответит ошибкой.

### Опции

| Опция | Назначение |
|---|---|
| `-d DIR` | папка с трейсом |
| `-a ADDR` | `unix:/путь/к/сокету` или `tcp:[HOST:]PORT` |
| `-c N` | число клиентских соединений (по умолчанию по одному на трейс; клиент `i` берёт трейс `i % число_трейсов`) |
| `-T SEC` | работать `SEC` секунд, прокручивая трейс по кругу |
| `-n LOOPS` | пройти каждый трейс `LOOPS` раз (по умолчанию 1, если нет `-T`) |
| `-V` | сверять каждый ответ побайтно с записью (только с фейковым сервером) |
| `-R` | цель — настоящий PostgreSQL |
| `-o FILE` | записать задержку каждого раунда (нс) в CSV |
| `-m N` | пропускать трейсы короче `N` раундов (по умолчанию 20). У клиента и сервера значение должно совпадать |

## Как устроен replay

- Трейс делится на **раунды**. Запрос — всё, что клиент отправил до сообщения Sync (`S`)
  или Query (`Q`) включительно. Ответ — всё, что сервер прислал до ReadyForQuery (`Z`)
  включительно. Раунд 0 — установка соединения.
- В режиме `-M prepared` один раунд — один SQL-оператор; транзакция pgbench (TPC-B) —
  около 7 раундов.
- Клиент — по одному потоку на соединение, как pgbench. Он отправляет раунд, ждёт `Z` и
  записывает время. Одновременно в работе не больше одного запроса.
- Сервер — по одному процессу на соединение (через `fork`, как postmaster). SQL он не
  выполняет: на каждый Sync отвечает следующим записанным ответом.
- Чтобы сервер знал, какой трейс отдавать, клиент первым делом отправляет 12-байтовый
  заголовок (`RPLY`, номер трейса, число раундов). С `-R` заголовок не отправляется.
- Для TCP включается `TCP_NODELAY`, как в libpq.

## Привязка к CPU и NUMA

Сервер и клиент — отдельные процессы, поэтому их можно разнести по ядрам или узлам.
Номера CPU и узлов смотрите в `lscpu` и `numactl --hardware`.

```bash
# одна NUMA-нода: разные наборы ядер
taskset -c <cpus-A> ./replay server -d trace/<запуск> -a unix:$PWD/replay.sock
taskset -c <cpus-B> ./replay client -d trace/<запуск> -a unix:$PWD/replay.sock -c 4 -T 10

# несколько NUMA-нод: сервер и клиент на одной ноде или на разных
numactl --cpunodebind=0 --membind=0 ./replay server ...
numactl --cpunodebind=1 --membind=1 ./replay client ...
```

## Ограничения

- Режим конвейера pgbench (`\startpipeline`) не поддерживается: сообщения без Sync в конце
  трейса игнорируются с предупреждением.
- Паузы между запросами из записи не воспроизводятся: клиент шлёт следующий запрос сразу.
- Трейсы с SSL/GSS-шифрованием не поддерживаются. Через UDS libpq его и не использует.

## Файлы

| Файл | Назначение |
|---|---|
| `record.sh` | запись трафика pgbench через socat |
| `rec_child.sh` | запускается socat на каждое соединение и пишет его байты в файлы (отдельный скрипт, потому что внутри `SYSTEM:` socat ломается на `:`) |

| `Makefile` | сборка `replay` |

| `pgsock/` | сокет PostgreSQL |
| `proxy/` | сокет прокси, существует только во время записи |
